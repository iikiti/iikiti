# Digital Asset Manager

The Digital Asset Manager (DAM) provides protected binary storage, CDN-ready HTTP delivery, responsive image and media processing, hierarchical organization, block editor and SEO integration, version history, usage tracking, SHA-256 deduplication, and rights/expiration enforcement.

First-party DAM plugins extend storage and media types:

- **S3-compatible object storage** (AWS S3, Cloudflare R2, MinIO, GCS S3-interop): see [`plugins/storage-s3.md`](plugins/storage-s3.md).
- **Audio & video processing** (FFmpeg/ffprobe metadata, poster frames, waveforms, optional HLS): see [`plugins/media-av.md`](plugins/media-av.md).

## Pluggable storage and access control

Binary originals and generated variants are persisted through `iikiti\CMS\Storage\AssetStorageInterface` (resolved at runtime via `DelegatingAssetStorage` and `AssetStorageRegistry`). Storage keys are generated by the application (`<2-hex>/<64-hex>.<ext>`); original filenames are stored as metadata only and direct filesystem paths are never exposed.

By default the active driver is `local` (`LocalAssetStorage`), storing files under `var/digital-assets` outside the public document root. Override the directory with the absolute `DIGITAL_ASSET_STORAGE_DIRECTORY` environment variable and back up that directory together with the database. Switch to a plugin-provided driver (such as `s3`, `r2`, or `gcs` from `iikiti-storage-s3`) with `ASSET_STORAGE_DRIVER`.

### Storage and delivery environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `DIGITAL_ASSET_STORAGE_DIRECTORY` | `<project_dir>/var/digital-assets` | Local filesystem root for the built-in `local` storage driver. |
| `ASSET_STORAGE_DRIVER` | `local` | Active `AssetStorageProviderInterface` driver key (`local`, `s3`, `r2`, `gcs`, or custom plugin driver). |
| `ASSET_DELIVERY_MODE` | `proxy` | `proxy` streams bytes through the CMS with full ETag/Range support; `redirect` issues HTTP `302 Found` redirects to a CDN or backend presigned URL when supported. |
| `ASSET_CDN_BASE_URL` | `""` | Optional public CDN base URL used for `public`, non-signed assets when `ASSET_DELIVERY_MODE=redirect`. |
| `ASSET_REDIRECT_TTL_SECONDS` | `300` | Lifetime (clamped to `1..3600` seconds) for backend presigned redirect URLs when `ASSET_DELIVERY_MODE=redirect`. |
| `ASSET_SIGNING_SECRET` | `""` | Dedicated HMAC-SHA256 secret for CMS signed URLs (`/assets/signed/...`). Falls back to `APP_SECRET` when empty. |
| `ASSET_EXPIRY_WARNING_DAYS` | `14` | Unified lead window (days before `expiresAt`) governing scheduled expiration warning alerts, `licenseStatus=expiring_soon|expiring_or_expired` filtering/facets, `license.isExpiringSoon`, and Admin UI badges (exposed as `expiryWarningDays` on `GET /api/admin/assets/sites`). |

### Site grants, visibility, and MFA

Every asset has explicit site-access grants (`digital_asset_site_grants`). The upload form grants the current site by default; administrators can grant additional sites they administer. A site administrator can manage an asset only when they administer every site granted access to it; global super administrators can manage assets and grants across sites. A grant controls which site's host can deliver the asset and which site's search can return it.

Visibility is separate from grants: new uploads default to `private`, requiring an authenticated user (who has completed any required MFA challenge) and a matching site grant. `public` assets may be fetched without authentication, but only from a granted site's host. External assets store a validated HTTPS URI and delivery redirects to that URI (`302 Found`); the CMS never downloads external content and external assets do not run local file processors.

## HTTP delivery, caching, byte ranges, and signed URLs

Asset delivery is served from `DigitalAssetFileController` via `AssetStreamResponseFactory`:

- `GET|HEAD /assets/{publicToken}/original`
- `GET|HEAD /assets/{publicToken}/{variant}`
- `GET|HEAD /assets/signed/{publicToken}/{variant}`

### Caching, ETags, and Range streaming

- **Strong ETags & conditional requests:** Responses include a strong `ETag` derived from the file's SHA-256 checksum. Matching `If-None-Match` requests return `304 Not Modified` without streaming file bytes.
- **Immutable `?v=` caching:** Public asset URLs that include a valid `?v=<checksum-prefix>` query parameter (`8..64` hexadecimal characters matching the file's SHA-256 checksum prefix) receive `Cache-Control: public, max-age=31536000, immutable`. Public asset requests without a matching `?v=` receive `Cache-Control: public, max-age=3600, stale-while-revalidate=86400`.
- **Private & signed responses:** Private assets, effectively private (expired `make_private`) assets, and signed URL deliveries always emit `Cache-Control: private, no-store`.
- **Byte-range streaming (`Range` / `206` / `416`) and `HEAD`:** Both local and remote storage backends advertise `Accept-Ranges: bytes`, support single RFC 9110 byte ranges (`206 Partial Content` with `Content-Range`), return `416 Range Not Satisfiable` (`Content-Range: bytes */<size>`) for unsatisfiable ranges, and handle `HEAD` requests without reading object bodies.
- **Safe headers:** Every response sends `X-Content-Type-Options: nosniff` and computes `Content-Disposition` via `AssetStreamResponseFactory::resolveDisposition()`, which strictly enforces `AssetMimeTypeRegistry::isInlineDeliverable()` (`inline` only for safe inline-deliverable MIME types such as images/audio/video; non-inline MIME types such as XML, PDF, text, CSV, and JSON are always downgraded to `attachment` even if `inline` is requested).
- **Redirect mode:** When `ASSET_DELIVERY_MODE=redirect`, public non-signed assets redirect (`302 Found`, `Cache-Control: private, no-store`) to `ASSET_CDN_BASE_URL` (or the backend's `publicUrl()`), and backends with `supportsTemporaryUrls()` redirect to a short-lived presigned URL bounded by `ASSET_REDIRECT_TTL_SECONDS`. If the backend does not support redirects (for example `local`), delivery falls back seamlessly to `proxy` streaming.

### Short-lived signed URLs

Administrators can mint temporary HMAC-SHA256 signed URLs (`AssetSignedUrlService`) to share private assets or force downloads without exposing session credentials:

```http
POST /api/admin/assets/{id}/signed-url
Content-Type: application/json

{
  "variant": "original",
  "ttlSeconds": 900,
  "disposition": "attachment",
  "siteId": 1,
  "version": 2
}
```

- `ttlSeconds` defaults to `900` and is bounded to `1..86400` seconds.
- `disposition` must be `inline` or `attachment`. `AssetStreamResponseFactory::resolveDisposition()` strictly enforces `isInlineDeliverable()`, so even signed URLs minted with `disposition: "inline"` downgrade non-inline MIME types (XML, PDF, text, CSV, JSON) to `attachment`.
- The generated URL (`/assets/signed/{publicToken}/{variant}?exp=...&site=...&d=...&sig=...`, plus optional `&v=...`) binds the token, variant, target site ID, expiration timestamp, disposition, and optional version using `ASSET_SIGNING_SECRET` (or `APP_SECRET` fallback) and constant-time verification (`hash_equals`).
- Signing requests require `ROLE_ADMIN`, asset management rights, site grant verification, and are logged through `AuditRecorder`.

### Consumer / API split delivery

In database-free `consumer` deployments (`APPLICATION_ROLE=consumer`), `DigitalAssetFileController` delegates `/assets/{publicToken}/{variant}` and `/assets/signed/{publicToken}/{variant}` to `PublicAssetApiProxy`, which proxies `GET` and `HEAD` requests to the API runtime (`PublicAssetController` at `/api/public/assets/...` and `/api/public/assets/signed/...`). When `iikiti-media-av` is active, `PublicAssetApiProxy::hls()` likewise proxies `/assets/{publicToken}/hls/{segment}` to `/api/public/assets/{publicToken}/hls/{segment}`. `PublicAssetApiProxy` forwards `v`, `exp`, `sig`, `site`, and `d` query parameters plus `If-None-Match`, `If-Modified-Since`, and `Range` request headers, and passes through `200`, `206`, `302`, `304`, and `416` responses along with `ETag`, `Cache-Control`, `Accept-Ranges`, `Content-Range`, `Location`, `Content-Type`, `Content-Disposition`, `Content-Length`, `Last-Modified`, and `Vary`.

## Uploads, supported content, and modern image processing

Allowed MIME types are aggregated by `AssetMimeTypeRegistry` from tagged `AssetMimeTypeProviderInterface` services. `CoreAssetMimeTypeProvider` registers 12 core types with a 25 MB (`26214400` bytes) default upload cap:

- **Images (inline):** `image/jpeg`, `image/png`, `image/gif`, `image/webp`, `image/avif`
- **Documents & text (attachment):** `application/pdf`, `text/plain`, `text/markdown`, `text/csv`, `application/json`, `application/xml`, `text/xml`

SVG and HTML are intentionally excluded to prevent stored XSS. Set PHP `upload_max_filesize`, `post_max_size`, and reverse-proxy body limits to at least the highest configured MIME limit (25 MB for core, or higher when [`iikiti-media-av`](plugins/media-av.md) is enabled).

### Modern image variants, focal-point crops, and ICC profiles

Migration `Version20261128020000` upgrades the default `image-thumbnails` workflow (`ImageThumbnailProcessor`, key `image_thumbnail`) to generate:

- **Named variants:** `thumbnail` (320×320) and `preview` (1280×1280).
- **Responsive width ladder:** `[320, 640, 960, 1280, 1920]` (`w320`, `w640`, `w960`, `w1280`, `w1920`), skipping widths larger than the source image so images are never upscaled.
- **Modern formats:** `avif` (quality `65`), `webp` (quality `80`), and `original` (JPEG quality `82`), emitted as e.g. `w640_avif`, `w640_webp`, `w640_jpg`. Writable formats are auto-detected via `magick -list format` so hosts without AVIF or WebP delegates skip unavailable encoders cleanly.
- **Focal-point smart cropping:** Normalized focal coordinates (`focalX`, `focalY` in `0.0..1.0`) stored on the asset drive `ImageThumbnailProcessor::computeFocalCropGeometry()` for fixed-aspect crop variants (`focal_crop = true` on `digital_asset_variants`), keeping the focal subject centered without clipping outside image bounds.
- **Color-accurate metadata stripping:** ImageMagick runs with `-auto-orient` and `+profile '!icc,*'` so embedded ICC color profiles are preserved while EXIF, GPS, IPTC, XMP, and comments are stripped from public variants.
- Each `DigitalAssetVariant` persists its SHA-256 `checksum`, `format`, `quality`, and `focal_crop` flag.

### EXIF/IPTC/XMP metadata, dominant color, BlurHash, and localized text

Migration `Version20261128020000` seeds the `image-metadata` workflow (`ImageMetadataProcessor`, key `image_metadata`) for `image/*` uploads:

- Extracts intrinsic `width` and `height` (accounting for EXIF orientation `5..8` dimension swaps).
- Extracts sanitized EXIF, IPTC, and XMP fields into `asset_media_metadata` (`JSONB`). **GPS coordinates are stripped by default** for privacy; opt in per workflow definition with `options.preserve_gps: true` only when geolocation metadata is explicitly needed.
- Computes a hex `dominantColor` (`#rrggbb`) and compact `blurhash` placeholder via `BlurHashEncoder`.
- Auto-fills empty `default_alt` and `default_caption` properties from XMP/IPTC/EXIF descriptions without overwriting administrator-supplied values.

`default_alt`, `default_caption`, and `description` are declared as BCP 47 localized object properties (`CoreObjectPropertyDefinitionProvider`). They store `LocalizedValue` translation maps (for example `{"en": "...", "fr-CA": "..."}`) and resolve according to the active render locale or the `?locale=<bcp47>` query parameter on admin and editor endpoints.

## Block Editor and SEO integration

### Site-scoped Editor Media API (`/api/editor/assets`)

Content editors with `Page:write` or `Template:write` permission can browse and upload DAM assets directly from the block editor without requiring `ROLE_ADMIN`. All responses and uploads are strictly scoped to the current site from `SiteRegistry`:

- `GET /api/editor/assets` — faceted search, filtering, and pagination (`?q=`, `mimeCategory`, `mimeType`, `folderId`, `collectionId`, `tagIds`, `sort`, `page`, `itemsPerPage`, `locale`)
- `GET /api/editor/assets/organization` — accessible folders, collections, and tags for the current site
- `GET /api/editor/assets/{id}` — single site-accessible asset details
- `POST /api/editor/assets/upload` — inline `multipart/form-data` upload granted to the current site (supports `duplicatePolicy`)
- `POST /api/editor/assets/check-duplicate` — SHA-256 pre-upload duplicate check scoped to the current site

### `MediaPickerControl` and responsive `<picture>` rendering

- The core `image` block uses `type: 'media'` (`MediaPickerControl` + `MediaPickerModal`), providing library browsing, folder/collection/tag filtering, inline drag-and-drop upload, external URL fallback, and an interactive click/keyboard focal-point selector.
- During server rendering, `BlockRenderer` uses `AssetRenderResolver::collectAssetIds()` to batch-prefetch all DAM assets and variants referenced in a block tree in two queries, eliminating N+1 queries.
- `templates/blocks/image.twig` calls the `iikiti_asset_media()` Twig helper (`BlockTwigExtension` → `AssetRenderResolver`) to render:
  - A `<picture>` element with `<source type="image/avif">` and `<source type="image/webp">` `srcset`/`sizes` lists when modern variants exist, followed by a fallback `<img>`.
  - Immutable `?v=<checksum-prefix>` URLs for cache busting on every variant and fallback `src`.
  - Intrinsic `width`/`height` attributes (preventing CLS), `style="object-position: <x>% <y>%"` from block or asset focal points, configurable `loading` (`lazy`/`eager`), `decoding`, and `fetchpriority` (`auto`/`high`/`low`).
  - Localized `alt` and `caption` fallbacks from the asset (`decorative: true` forces `alt=""`).
  - Private assets render only when `editor_mode` is true and are omitted on public pages.

### SEO social image binding (`iikiti-content-optimization`)

Open Graph (`og:image`) and X/Twitter (`twitter:image`) image settings in `iikiti-content-optimization` accept either an external HTTPS/root-relative URL or a structured DAM reference (`{ "source": "asset", "assetId": 42 }`) at page, site, and application levels. `SeoMetadataResolver`:

- Resolves only `public`, site-granted assets (never leaking private or ungranted assets to social crawlers).
- Prefers social-crawler-compatible JPEG/PNG/GIF renditions (`preview`, `w1280_jpg`/`w1280_png`, or `original`) over AVIF/WebP.
- Emits versioned canonical URLs along with `og:image:width`, `og:image:height`, and `og:image:alt` (using the asset's localized `default_alt` when no explicit override is set).

## DAM organization, faceted search, and bulk operations

Migration `Version20261128030000` introduces three `DbObject` organization entities managed through `DigitalAssetOrganizationController` (`/api/admin/assets/...`, `ROLE_ADMIN`):

- **Folders (`DigitalAssetFolder`):** Hierarchical folders with materialized paths (`/campaigns/2026-launch`) and optional per-site grants (`digital_asset_folder_site_grants`; empty grants mean global, manageable by global admins). Moving or renaming a folder updates descendant paths.
  - `GET /api/admin/assets/folders`, `POST /api/admin/assets/folders`, `PUT /api/admin/assets/folders/{id}`, `DELETE /api/admin/assets/folders/{id}`
- **Collections (`DigitalAssetCollection`):** Curated lightboxes/galleries linking assets many-to-many (`digital_asset_collection_items`).
  - `GET /api/admin/assets/collections`, `POST /api/admin/assets/collections`, `PUT /api/admin/assets/collections/{id}`, `DELETE /api/admin/assets/collections/{id}`
  - `POST /api/admin/assets/collections/{id}/items`, `DELETE /api/admin/assets/collections/{id}/items/{assetId}`
- **Tags (`DigitalAssetTag`):** Namespaced tags unique by `(tag_namespace, tag_slug)` (default namespace `asset`), linked many-to-many via `digital_asset_tags`.
  - `GET /api/admin/assets/tags`, `POST /api/admin/assets/tags`, `PUT /api/admin/assets/tags/{id}`, `DELETE /api/admin/assets/tags/{id}`

### Faceted search and sorting

`GET /api/admin/assets` (and `GET /api/editor/assets`) accepts `DigitalAssetFilterCriteria` query parameters:

- `q` (or `query`): text search across asset `title`, `originalName`, and linked tag names/slugs
- `mimeCategory`: `image`, `video`, `audio`, `document`, `text`, `data`, or `other`
- `mimeType`: exact MIME type filter
- `siteId`, `visibility` (`public`|`private`), `processingStatus` (`pending`|`processing`|`complete`|`failed`)
- `folderId` (numeric ID or `unfiled`), `unfiledOnly=1`, `includeSubfolders=1`
- `collectionId`, `tagIds` (comma-separated or array)
- `licenseStatus`: `valid`, `expiring_soon`, `expiring_or_expired`, `expired`, or `missing`
- `sort`: `newest` (default), `oldest`, `title_asc`, `title_desc`, `size_desc`, `size_asc`
- `page`, `itemsPerPage` (max `100`), `locale` (BCP 47)

### Bulk operations

`POST /api/admin/assets/bulk` (`DigitalAssetBulkActionService`) executes batch mutations on up to `500` asset IDs per request. Authorization (`DigitalAssetAccessPolicy::canManageAsset()`) is verified for every asset individually, returning `{ succeeded: [...], failed: [{ id, reason, usages? }] }` without aborting valid items.

Supported actions: `tag_add`, `tag_remove`, `move_folder`, `collection_add`, `collection_remove`, `set_visibility`, `set_site_grants`, `reprocess`, and `delete` (enforces the usage conflict guard unless `force: true`).

### Admin workspace UX

The **Assets** admin screen (`/assets`) provides:

- A collapsible organization sidebar for browsing folders (tree view), collections, tags, and unfiled assets.
- A toolbar with Grid/List view toggle, faceted filter chips, sorting, and instant search.
- A drag-and-drop multi-file `UploadDropzone` with per-file progress, folder/visibility/site-grant selection, and pre-upload duplicate detection.
- Multi-select checkboxes with a floating `BulkActionBar` for tagging, moving, visibility/grant updates, reprocessing, and deletion.
- A tabbed `AssetDetailModal` for editing localized alt/caption/description, focal point, organization, version history / replace-in-place, "Where Used" references, licensing & expiration, and signed URL generation.

## Versioning, usage tracking, deduplication, and rights management

Migration `Version20261128040000` adds `digital_asset_versions`, `digital_asset_usages`, checksum/expiration indexes, and rights/versioning columns on `objects`.

### Asset versioning and replace-in-place

Uploaded assets maintain immutable version snapshots in `digital_asset_versions` (`DigitalAssetVersionManager`). Backfill migration `Version20261128040000` records version `1` for existing uploaded assets.

- **`POST /api/admin/assets/{id}/replace`** (`multipart/form-data`: `file`, optional `changeNote`, optional `allowMimeChange=1`):
  - Keeps the asset's numeric `id` and `publicToken` unchanged so existing page/block/SEO references continue working without broken links.
  - Preserves previous version binaries in storage, increments `currentVersion`, updates `checksum`/`size`/`mimeType`, invalidates `RenderedFragmentCache`, queues reprocessing for fresh variants, and dispatches `DigitalAssetEvents::REPLACED`.
  - Because rendered URLs carry `?v=<checksum-prefix>`, clients and CDNs immediately fetch the replaced bytes.
- **`GET /api/admin/assets/{id}/versions`**: lists all stored versions with checksums, dimensions, change notes, creator IDs, and timestamps.
- **`POST /api/admin/assets/{id}/versions/{versionNumber}/rollback`** (optional JSON `{ "changeNote": "..." }`): restores a historical version's binary as a new incremented active version (preserving full history), re-queues processing, and invalidates rendered fragment caches.
- **`GET /api/admin/assets/{id}/versions/{versionNumber}/download`**: streams a specific historical version as an attachment (`Cache-Control: private, no-store`).

### Usage tracking ("Where Used") and deletion safety guard

`AssetUsageIndexer` maintains `digital_asset_usages` via `AssetUsageIndexSubscriber` whenever Pages, Templates (draft and published block trees and settings), Sites, or Applications are saved or deleted. Built-in extractors (`BlockTreeAssetUsageExtractor`, `SettingsAssetUsageExtractor`) and plugin-provided `AssetUsageExtractorInterface` services detect both numeric `assetId` references and 64-hex `publicToken` URL references.

- **`GET /api/admin/assets/{id}/usage`**: returns `usageCount` and a list of `AssetUsageReference` entries (`contextType`, `contextId`, `contextTitle`, `fieldPath`, `isDraft`, `siteId`, `editUrl`).
- **Deletion conflict guard:** `DELETE /api/admin/assets/{id}` refuses to delete an asset that still has recorded usages, returning HTTP `409 Conflict` with `{ error, usageCount, usages }`. Pass `?force=1` (or `force: true` on bulk `delete`) to override the guard; forced deletions are recorded in the audit log.
- **Rebuilding the index:** After bulk database imports, upgrades, or adding a new plugin `AssetUsageExtractorInterface`, rebuild the usage table with:

```sh
php bin/console iikiti:asset:usage:rebuild
```

### SHA-256 duplicate detection

Uploaded files are indexed by their SHA-256 digest (`idx_objects_asset_checksum`).

- **Pre-upload probe:** `POST /api/admin/assets/check-duplicate` (or `POST /api/editor/assets/check-duplicate`) accepts `{ "checksum": "<64-hex-sha256>" }` and returns `{ duplicate: bool, matches: [...] }` for matching assets accessible to the caller's sites.
- **Upload `duplicatePolicy`:** `POST /api/admin/assets/upload` and `POST /api/editor/assets/upload` accept a `duplicatePolicy` form field:
  - `allow` (default): store the upload as a new asset.
  - `reject`: abort the upload with HTTP `409 Conflict` and return matching existing assets.
  - `reuse`: return the existing accessible asset without storing a duplicate binary.

### Rights management and scheduled expiration

Assets support structured licensing metadata via `PUT /api/admin/assets/{id}`:

- `licenseType` (up to 64 chars, e.g. `royalty-free`, `rights-managed`, `cc-by-4.0`)
- `licenseHolder`, `licenseUrl`, `licenseNotes`
- `expiresAt` (ISO-8601 timestamp)
- `expiryAction`: `alert` (notify and audit only) or `make_private` (notify, audit, and automatically revoke public delivery)

Expiration is enforced at two layers:

1. **Scheduled background check (`CheckExpiringDigitalAssets`):** `DefaultScheduleProvider` schedules `CheckExpiringDigitalAssets` every hour through Symfony Scheduler (`scheduler_default`). `CheckExpiringDigitalAssetsHandler`:
   - Scans assets expiring within `ASSET_EXPIRY_WARNING_DAYS` (default `14`) and sends notifications, warning logs, and audit entries idempotently (tracked via `expiryNotifiedAt`).
   - Scans newly expired assets (`expiredHandledAt IS NULL`), records audit entries, dispatches `DigitalAssetEvents::EXPIRED`, and—when `expiryAction` is `make_private`—flips `visibility` to `private` and invalidates `RenderedFragmentCache`.
2. **Request-time enforcement:** `AbstractDigitalAsset::isEffectivelyPrivate()` checks `expiresAt <= now` whenever `expiryAction === 'make_private'`. `DigitalAssetFileController`, `PublicAssetController`, `HlsDeliveryController`, `AssetRenderResolver`, and `SeoMetadataResolver` all evaluate `isEffectivelyPrivate()`, so expired `make_private` assets are immediately blocked from unauthenticated delivery, HLS playback, public block rendering, and social metadata even before the next hourly scheduler tick executes.

## Background processing and events

Install ImageMagick with the `magick` command and Poppler utilities with `pdftotext` on every worker host. ImageMagick runs with argument arrays and a timeout; uploaded images are dimension-checked and variants are bounded to 4096×4096. PDF extraction is limited by page count, time and output bytes. Plain-text extraction is bounded to 5 MB (1 MB by default). Configure external binary paths through the worker's `PATH`.

After migrations, initialize Messenger's Doctrine transport. A persistent worker is the recommended option for reliable background throughput:

```sh
php bin/console doctrine:migrations:migrate
php bin/console messenger:setup-transports
php bin/console messenger:consume asset_processing --time-limit=3600
```

After every code deployment, rebuild the container and restart running workers so they pick up changed service constructors and compiled workflow definitions:

```sh
composer lint:container
php bin/console cache:clear
php bin/console messenger:restart-workers
```

`composer lint:container` verifies the container compiles (run it after dependency updates too: the asset aggregate state machine is attribute-defined, and runtime graphs are compiled from versioned definitions).

The generic batch worker, Symfony Scheduler, and optional audio/video HLS transcoder have separate Messenger receivers:

```sh
php bin/console messenger:consume batch_processing --time-limit=3600
php bin/console messenger:consume scheduler_default --time-limit=3600
php bin/console messenger:consume media_transcoding --time-limit=3600
```

After deployment, apply Doctrine migrations and run `php bin/console messenger:setup-transports` before starting these workers.

Symfony Scheduler is the default project scheduler. It emits a minute tick that checks persisted recurring schedules (`RunDueBatchSchedules`), an hourly tick for `CheckExpiringDigitalAssets`, and a daily tick for `EnsureObjectPartitions`. Select another registered backend with `SCHEDULER_ADAPTER`; an alternate backend must invoke the shared schedule runner so occurrence claims prevent duplicate dispatch. Schedule definitions are backend-neutral and use cron expressions plus an IANA time zone.

For installations without cron or a persistent worker, the CMS defaults to a lazy background tick after eligible web responses. It checks due schedules and consumes a bounded number of messages from configured Messenger receivers. The HTTP response is sent first, but the PHP worker remains occupied while this small tick runs. `BACKGROUND_RUNNER_MAX_MESSAGES` (default `5`), `BACKGROUND_RUNNER_TIME_LIMIT_SECONDS` (default `2`), and `BACKGROUND_RUNNER_COOLDOWN_SECONDS` (default `5`) bound and throttle the work. The `failed` receiver is excluded by default; add any other receiver names (such as `media_transcoding` when HLS is enabled) to `BACKGROUND_RUNNER_EXCLUDED_RECEIVERS` as a comma-separated list to keep them for dedicated workers.

Lazy execution is traffic-triggered: if the site receives no requests and no external runner is active, queued work remains pending. Missed schedule occurrences are retained and caught up incrementally within the per-tick limits. To use a one-shot OS cron instead, apply migrations and run this command at the desired cadence (for example, once per minute), then disable the web fallback:

```sh
php bin/console doctrine:migrations:migrate
php bin/console messenger:setup-transports
php bin/console iikiti:maintenance:run
```

### Lifecycle state machine, workflows, and events

The aggregate asset lifecycle remains a Symfony 8.2 attribute state machine in `src/StateMachine/AssetProcessingStateMachine.php`, marking `AbstractDigitalAsset::processingStatus` (`pending` → `processing` → `complete`/`failed`). `process` and `requeue` stay reachable from every state so Messenger redeliveries can run; `complete` and `fail` require `processing`.

Individual processor rules are versioned generic workflow definitions. Their `metadata.assetProcessor` records a registered `processorKey`, MIME pattern, conditions, options, and site scope. A run is a generic `WorkflowInstance` whose registered subject reference is `digital_asset:<id>` and whose marking is `pending`/`running`/`complete`/`failed`/`skipped`. The `start` transition is retryable from `pending`, `running`, `failed`, and `skipped`; attempt/error bookkeeping is applied by transition metadata. Completed runs are not processed again for the same rule/asset idempotency key.

The generic workflow API is documented in [`workflow-admin.md`](workflow-admin.md). Asset-detail responses expose `workflowInstances` (definition key/version, marking status, execution state, attempts, and error).

The migrated defaults run `image-metadata` (`image_metadata`) and `image-thumbnails` (`image_thumbnail`) for supported images, and extract text from PDFs and supported text formats (`pdf_text`, `plain_text`). Messenger retries failed jobs and moves exhausted messages to its failure transport. Processor implementations remain tagged code services using `DigitalAssetProcessorInterface`; the `AssetWorkflowDefinition` argument is a non-persisted compatibility value object, not a Doctrine entity.

Lifecycle events are dispatched through Symfony EventDispatcher and can be subscribed to by core or plugin services:

- `DigitalAssetEvents::CREATED` (`iikiti.digital_asset.created`)
- `DigitalAssetEvents::UPDATED` (`iikiti.digital_asset.updated`)
- `DigitalAssetEvents::DELETED` (`iikiti.digital_asset.deleted`)
- `DigitalAssetEvents::REPLACED` (`iikiti.digital_asset.replaced`)
- `DigitalAssetEvents::EXPIRED` (`iikiti.digital_asset.expired`)
- `DigitalAssetEvents::PROCESSING_STARTED` (`iikiti.digital_asset.processing_started`)
- `DigitalAssetEvents::PROCESSING_COMPLETED` (`iikiti.digital_asset.processing_completed`)
- `DigitalAssetEvents::PROCESSING_FAILED` (`iikiti.digital_asset.processing_failed`)

Each event receives a `DigitalAssetEvent` with `getAsset()`. Custom processors implement `DigitalAssetProcessorInterface`, provide a unique processor key and `supportsMimePattern()`, and are tagged automatically. Rule configuration can invoke only registered processor services; it cannot execute configured code.

Manage processor definitions under the generic `/api/admin/workflows/definitions` API and the Workflows admin screen. Global asset rules use `allSites: true`; site-owned rules apply only to assets granted to that site. The graph editor offers only registered asset processor keys. Built-in processors validate supported MIME patterns, dimensions, pages, and output limits; plugin processors may provide their own typed options.

Migration `Version20261015002000` backfills legacy asset rules and runs into generic workflow definition versions and instances. After code/UI cutover and count verification, `Version20261015003000` removes the legacy `digital_asset_workflows` and `digital_asset_workflow_runs` tables. Do not apply the contract migration before the generic backfill is verified.

## Site transfer

The Site Transfer admin screen creates resumable batch exports/imports. The versioned NDJSON manifest contains site/object IDs, selected object properties, and source API paths for DAM assets; it never contains file bytes. Export manifests are stored under `var/site-transfers`, outside the public directory. The source API exposes the file stream at `/api/admin/site-transfer/exports/{exportId}/assets/{assetId}`.

The importing server must use HTTPS and provide an API token whose user has access to the selected export and can manage the requested assets. Asset grants are checked again for each download. A 403/404 skips the complete asset record and records the source asset ID and reason; it does not stop unrelated content. A 401 pauses the import and asks for a refreshed source token. Tokens are encrypted with the application's transfer-credential key, held only while the job is active, never put in a URL or event, and deleted on completion/cancellation.

Remote requests reject private/loopback addresses and redirects, and uploaded asset streams are MIME-checked, size-checked against `AssetMimeTypeRegistry`, checksum-verified, and written through the active `AssetStorageInterface` backend. External assets keep their HTTPS URI metadata; they are not downloaded as binary files. A transfer user must be able to manage all sites in an asset's grants, matching normal DAM management rules.

Imports map source identities to a selected existing destination site or, for super/system admins, a newly created site. Re-imports upsert records previously imported from that source, preserve unselected properties, and never delete destination-only records. Users can select transferable object types and properties on both export and import. Users, roles, API tokens, audit entries and workflow runtime history are excluded. Unresolved object references and skipped assets appear in the batch job's review issues.

## Search indexing

The migration adds an `asset_content` property field to existing search indexes. Extracted PDF/text content is stored as the bounded `extracted_text` object property and indexed by the existing PostgreSQL search engine. Search results enforce the current site's grants and public/private visibility; private assets are included only by the admin search path. The extracted body is used for matching but is not returned in search hit data. Search autocomplete excludes assets.
