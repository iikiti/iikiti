# Digital Asset Manager

## Storage and access

Uploaded originals and generated variants are stored under `var/digital-assets`, outside the public document root. Override the directory with the absolute `DIGITAL_ASSET_STORAGE_DIRECTORY` environment variable. Back up this directory together with the database. Storage keys are generated by the application; original filenames are metadata only.

Every asset has explicit site-access grants. The upload form grants the current site by default; administrators can grant additional sites they administer. A site administrator can manage an asset only when they administer every site granted access to it; global super administrators can manage assets and grants across sites. A grant controls which site's host can deliver the asset and which site's search can return it. Visibility is separate: new uploads are `private`, requiring an authenticated user and a matching site grant. `public` assets may be fetched without authentication, but only from a granted site's host. Direct filesystem URLs are never exposed.

File delivery uses `/assets/{publicToken}/original` or `/assets/{publicToken}/{variant}` on the site's domain. External assets store a validated HTTPS URI and delivery redirects to that URI; the CMS never downloads external content. External assets cannot run local file processors.

## Uploads and supported content

The admin upload API accepts files up to 25 MB and checks the detected MIME type. Set PHP `upload_max_filesize`, `post_max_size` and any reverse-proxy request-body limit to at least 25 MB. Initial supported types are JPEG, PNG, GIF and WebP images; PDF; plain text, Markdown, CSV, JSON and XML. SVG and HTML are intentionally not accepted. The admin form creates either an upload or an HTTPS external link, and supports title, visibility and one-or-more site grants.

Management endpoints require an authenticated administrator (`ROLE_ADMIN`):

- `GET /api/admin/assets?page=1&itemsPerPage=25`
- `GET /api/admin/assets/{id}`
- `POST /api/admin/assets/upload` (`multipart/form-data`: `file`, `title`, `visibility`, `siteIds` as a JSON array)
- `POST /api/admin/assets/uri` (JSON: `uri`, `title`, optional `mimeType`, `visibility`, `siteIds`)
- `PUT /api/admin/assets/{id}` (JSON metadata, grants and external URI)
- `DELETE /api/admin/assets/{id}`
- `GET /api/admin/assets/sites`

Deletion removes the original, generated variants, durable workflow instances (including task/history records), and search entries.

## Background processing and events

Install ImageMagick with the `magick` command and Poppler utilities with `pdftotext` on every worker host. ImageMagick runs with argument arrays and a timeout; uploaded images are dimension-checked and variants are bounded to 4096×4096. PDF extraction is limited by page count, time and output bytes. Plain-text extraction is bounded to 5 MB (1 MB by default). Configure external binary paths through the worker's `PATH`.

After migrations, initialize Messenger's Doctrine transport and run a worker:

```sh
php bin/console doctrine:migrations:migrate
php bin/console messenger:setup-transports
php bin/console messenger:consume asset_processing --time-limit=3600
```

After every code deployment, rebuild the container and restart running workers so they pick up changed service constructors and compiled workflow definitions:

```sh
composer lint:container
php bin/console cache:clear
php bin/console messenger:restart-workers
```

`composer lint:container` verifies the container compiles (run it after dependency updates too: the asset aggregate state machine is attribute-defined, and runtime graphs are compiled from versioned definitions).

The generic batch worker and Symfony Scheduler have separate Messenger receivers:

```sh
php bin/console messenger:consume batch_processing --time-limit=3600
php bin/console messenger:consume scheduler_default --time-limit=3600
```

After deployment, apply Doctrine migrations and run
`php bin/console messenger:setup-transports` before starting these workers.

Symfony Scheduler is the default project scheduler. It emits a minute tick that
checks the persisted recurring schedules. Select another registered backend
with `SCHEDULER_ADAPTER`; an alternate backend must invoke the shared schedule
runner so occurrence claims prevent duplicate dispatch. Schedule definitions
are backend-neutral and use cron expressions plus an IANA time zone.

## Site transfer

The Site Transfer admin screen creates resumable batch exports/imports. The
versioned NDJSON manifest contains site/object IDs, selected object properties,
and source API paths for DAM assets; it never contains file bytes. Export
manifests are stored under `var/site-transfers`, outside the public directory.
The source API exposes the file stream at
`/api/admin/site-transfer/exports/{exportId}/assets/{assetId}`.

The importing server must use HTTPS and provide an API token whose user has
access to the selected export and can manage the requested assets. Asset grants
are checked again for each download. A 403/404 skips the complete asset record
and records the source asset ID and reason; it does not stop unrelated content.
A 401 pauses the import and asks for a refreshed source token. Tokens are
encrypted with the application's `APP_SECRET`, held only while the job is
active, never put in a URL or event, and deleted on completion/cancellation.

Remote requests reject private/loopback addresses and redirects, and uploaded
asset streams are limited to the existing 25 MB upload maximum, MIME-checked,
checksum-verified and written to protected asset storage. External assets keep
their HTTPS URI metadata; they are not downloaded as binary files. A transfer
user must be able to manage all sites in an asset's grants, matching normal DAM
management rules.

Imports map source identities to a selected existing destination site or, for
super/system admins, a newly created site. Re-imports upsert records previously
imported from that source, preserve unselected properties, and never delete
destination-only records. Users can select transferable object types and
properties on both export and import. Users, roles, API tokens, audit entries
and workflow runtime history are excluded. Unresolved object references and
skipped assets appear in the batch job's review issues.

The aggregate asset lifecycle remains a Symfony 8.2 attribute state machine in `src/StateMachine/AssetProcessingStateMachine.php`, marking `AbstractDigitalAsset::processingStatus` (`pending` → `processing` → `complete`/`failed`). `process` and `requeue` stay reachable from every state so Messenger redeliveries can run; `complete` and `fail` require `processing`.

Individual processor rules are versioned generic workflow definitions. Their `metadata.assetProcessor` records a registered `processorKey`, MIME pattern, conditions, options, and site scope. A run is a generic `WorkflowInstance` whose registered subject reference is `digital_asset:<id>` and whose marking is `pending`/`running`/`complete`/`failed`/`skipped`. The `start` transition is retryable from `pending`, `running`, `failed`, and `skipped`; attempt/error bookkeeping is applied by transition metadata. Completed runs are not processed again for the same rule/asset idempotency key.

The generic workflow API is documented in `workflow-admin.md`. Asset-detail responses expose `workflowInstances` (definition key/version, marking status, execution state, attempts, and error) instead of the removed asset-specific `workflowRuns` shape.

The migrated defaults generate 320×320 thumbnails and 1280×1280 previews for supported images, and extract text from PDFs and supported text formats. Messenger retries failed jobs and moves exhausted messages to its failure transport. Processor implementations remain tagged code services using `DigitalAssetProcessorInterface`; the `AssetWorkflowDefinition` argument is now a non-persisted compatibility value object, not a Doctrine entity.

Lifecycle events are dispatched through Symfony EventDispatcher and can be subscribed to by core or plugin services:

- `DigitalAssetEvents::CREATED`
- `DigitalAssetEvents::UPDATED`
- `DigitalAssetEvents::DELETED`
- `DigitalAssetEvents::PROCESSING_STARTED`
- `DigitalAssetEvents::PROCESSING_COMPLETED`
- `DigitalAssetEvents::PROCESSING_FAILED`

Each event receives a `DigitalAssetEvent` with `getAsset()`. Custom processors implement `DigitalAssetProcessorInterface`, provide a unique processor key and `supportsMimePattern()`, and are tagged automatically. Rule configuration can invoke only registered processor services; it cannot execute configured code.

The old `/api/admin/asset-workflows` endpoints are removed. Manage processor definitions under the generic `/api/admin/workflows/definitions` API and the Workflows admin screen. Global asset rules use `allSites: true`; site-owned rules apply only to assets granted to that site. The graph editor offers only registered asset processor keys. Built-in processors validate supported MIME patterns, dimensions, pages, and output limits; plugin processors may provide their own typed options.

Migration `Version20261015002000` backfills existing asset rules and runs into generic workflow definition versions and instances. After code/UI cutover and count verification, `Version20261015003000` removes the legacy `digital_asset_workflows` and `digital_asset_workflow_runs` tables. Do not apply the contract migration before the generic backfill is verified.

## Search indexing

The migration adds an `asset_content` property field to existing search indexes. Extracted PDF/text content is stored as the bounded `extracted_text` object property and indexed by the existing PostgreSQL search engine. Search results enforce the current site's grants and public/private visibility; private assets are included only by the admin search path. The extracted body is used for matching but is not returned in search hit data. Search autocomplete excludes assets.
